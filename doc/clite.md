# Web 应用的另一种选择
我讨厌复杂。
一方面，是因为我能力有限，面对复杂的东西，我会有挫败感；
另一方面，有些东西本来很简单，但被复杂化了。

这几天，React 被发现有严重的安全漏洞，说实话我是有点幸灾乐祸的。
它太复杂了，很难不出问题。
React 的作者们的确是超一流的开发者，但也是人类。
优秀的人类也会犯错，这很正常，这也不影响他们的优秀。

### RSC 之前的 React
> RSC: React Server Components

那是“低糖”的 React，几乎没有“额外的语法”，
只要学会 js（至少要理解闭包），几乎不用学其他的东西。

> 其他的“前端框架”，比如 Vue，它把 js 里一些丑陋的特性藏起来，
精心制作了很多“更符合直觉”的语法，也就是“加糖”。
糖是甜的，但会成瘾。
丑陋的特性被藏起来，用户不用面对，也就不需要理解。
所以熟练掌握 Vue 的人，不需要深入理解 js，容易被 Vue 绑死，离不开 Vue。
而 React 的糖度很低，你必须先深入理解 js，然后 React... 你几乎已经熟练掌握了。
“必须先深入理解 js”，这也是很多人说 React 学习路径比较陡峭的原因。

jsx 算 React 的“额外的语法”，虽然丑陋，但形式上跟 html 很像，里面夹杂的 js 也是纯正的 js。
总的来说，jsx 很丑，但很简单，很实用。

hook 才是 React 真正的“额外语法”，
它规定了一些函数（即 hook）只能在特定的位置调用
（即 function component 最外层、同步执行路径中调用，不能放在条件、循环或嵌套函数里）。
但好在 hook 不算多，而且功能单纯。

那时候，用 React 开发 Web 应用，开发者更容易理解“React 帮我做了什么”（这里说的“更容易”是和现在相比）。
其实就是简单的 `state + function = view`。

### 全栈 React

RSC 之前的 React 和其他“前后端分离”的前端框架共享很多问题：
+ SEO（没有流量简直就没有命）
+ 有些逻辑（如路由、权限检查），后端处理一遍、前端还要再处理一遍
+ 部署时，前端一套、后端一套、再来个 nginx
+ 首屏性能
+ ...

再加上成熟且流行的 Node.js（前后端统一语言）和 ts（前后端共享代码），分离了几年了的前后端，复合的诱惑实在太大了。

但对我来说，RSC 这一步太过头了，前后端的界限几乎模糊了。
Next.js 向我展示了各种眼花缭乱的操作，
它告诉我很多“只要 xxx，就能 yyy”。
但我再也不像以前那样“明确知道每行代码的意义”了，
我甚至都搞不清楚这行代码是在服务器里运行，还是在浏览器里运行。

开发者不理解自己的代码，还有比这更烦人的事吗？

### 没有 silver bullet

是的没有 silver bullet！
我只是尝试解释“新老 React 为什么不是 silver bullet”。
否定或神化 React 同样愚蠢。

### clite
clite: client lite

React 的 RSC 这一步迈得太大，
于是我思考“这一步应该怎么迈”，
于是就有了 clite 这堆儿不系统的念头。

clite 不是“更好的 client”。
相反，clite 是更弱的 client。
弱、简陋，但在某些场景很实用。
